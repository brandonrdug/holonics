# Complete C++/CUDA engine construction roadmap

**Authority:** ratified construction plan for the new pure engine.

**Truth status:** owner boundaries, invariants, gates, and required receipts are
`project-postulate`. Standard mathematical laws retain the grades declared in `canon/`. Existing
capabilities remain `established-bounded` under `canon/06_ESTABLISHED_CAPABILITIES.md`. A phase is
not established merely because this plan describes it.

**Terminal consequence:** completion returns the project to—and closes—the point at which the
prior Soma construction faltered: one continuing GPU-resident holonic body receives a real
mathematical question, emits actual Lean theorem/proof source through an exterior codec, receives
the real kernel result as a caused return, changes reusable morphology, rests/remounts without its
developmental sources, and emits a second real theorem/proof whose construction requires the first
returned theorem fiber. Both artifacts and their complete causal-information receipts are
returned conversationally.

This is not a plan to build a Lean engine, a language engine, a repository engine, or a CPU program
which later acquires a GPU backend. It is the construction of one exact physical information
ecology. C++, CUDA, files, text, Lean, and the operating system are apparatus or codec charts around
that body.

## 1. What Brandon's corrections require

The recent failure history fixes the following requirements in the construction.

### 1.1 Seriality is local; the deed is a weave

A thread remains serial along its caused chronology. The engine must not annihilate serial order.
It must prevent one thread, one source scan, one host loop, or one global queue from owning the
total higher-order consequence. Co-present locally serial currents form a warp/weft ecology;
crossings execute together only when independence or interaction has been established.

The practical consequence is receiver-bounded sparse fronts on the GPU, exact serial port gluing
between fronts, and explicit interchange certificates inside a front. Worker count, queue
membership, or launch order proves nothing.

### 1.2 Stored bytes are not the navigable body

A repository is a file store and an exterior source chart. It must not remain the runtime topology.
Mounting founds stable occurrence/incidence charts from its material, incrementally and in parallel.
Paths, byte offsets, filenames, and serialization order remain source testimony; none becomes
semantic identity or the machine's scheduler.

Broad material is not “tokenized into a model.” It is admitted as plural situated occurrences,
local relations, boundaries, alternate charts, and obstruction. Different charts are retained
because different receivers need different routes. No one chart is the canonical interior.

### 1.3 Algorithms are enacted physical transport

Computer science is not detached from physics. An algorithm is a causal geometry enacted by
physical apparatus: local state, permitted transit, finite communication, synchronization,
resource pressure, and returned consequence. The GPU is the primary physical ecology because the
work is wide local incidence and geometric/algebraic transport. The CPU does not own control,
language, mathematics, or the algorithm; it performs named exterior crossings and lifecycle I/O.

### 1.4 Lean and language have no semantic privilege

Lean is an exterior mathematical codec and checker. Human prose, Lean syntax, UTF-8, declaration
graphs, proof terms, kernel messages, and executable instructions are different receiver faces of
caused material. Lean may run on a CPU because the external Lean executable is a CPU apparatus;
that does not move the engine's mathematical construction or learning to the CPU. The checker
returns a world occurrence exactly as a sensor or laboratory instrument would.

There is no core type called `Language`, `LeanTask`, `ProofPhase`, `RepositoryWorld`, or
`AcceptedCount`. Kernel acceptance is a typed returned relation attached to one generated passage,
not a scalar gate or a scheduler phase.

### 1.5 Learning is returned morphological change

Mounting, exposure, training, and reference remain distinct. No training claim is admitted until a
returned occurrence changes reusable local morphology, later conduct differs under a declared
receiver, the change survives native rest/remount, developmental sources are absent, and an
excluding-fiber ablation removes the claimed later consequence.

### 1.6 Purity removes sunk-cost contamination

There is one current schema. No compatibility readers, version fallbacks, renamed adapters, dual
writers, or preserved rejected owners are built. Dead or superseded code is deleted immediately
after its evidence is committed. The historical Rust implementation is evidence and a source of
exact counterexamples; it is never linked, wrapped, translated wholesale, or kept as a second
production body.

### 1.7 Exactness is bit-pure

No floating-point operation exists in the semantic/device-core dependency cone. A float may not
choose control flow, index, topology, coefficient, promotion, identity, or any bit later committed
to standing. Exact integers, dynamic limbs, rationals, finite fields, quotient rings, polynomials,
projective pairs, proof objects, and certified bounds carry the engine. Approximate exterior
measurements cross only as calibrated integer/rational enclosures with an open remainder.

## 2. Completion deed and non-substitutable receipts

3. The engine opens an exact continuation fiber containing its locally caused alternatives and
   obstructions.
4. GPU-resident mathematical currents construct a new theorem statement/proof passage `g₁` not

5. The complete emitted Lean source is returned to the user and sent through the Lean codec port.

7. `r₁` resumes the same pending deed and commits a lineaged morphology delta `Δm₁`.
8. The body rests natively, developmental/source material departs, and the body remounts without
   replay.

### 2.2 Deed B

1. A second request `q₂` opens after the remount.
2. The receiver contract declares the exact dependency on the returned `g₁/r₁` fiber.
3. The changed body emits a new theorem/proof passage `g₂` and its Lean source.
4. The real kernel response `r₂` returns and is committed.
5. An ablation excluding `Δm₁` makes the declared `g₂` consequence unavailable or changes it in
   the predicted exact way; version identity, lineage length, or timing alone cannot satisfy this.

## 5. Continuous architectural enforcement

Phase R0 builds `holonic-audit`, a source/build/binary audit invoked before and after every phase.
It fails the build on:

- `float`, `double`, half/tensor-float types, floating intrinsics, or floating PTX/SASS operations
  in the semantic/device dependency closure;
- copy construction/assignment for body, continuation, pending deed, live morphology, resident
  world, codec environment, or rest ownership;
- semantic-core identifiers tied to Lean, language, repository, CPU, GPU, filenames, or display;
- public semantic ownership by raw `std::vector`, maps, sets, queues, or application registries;
- forbidden dependency edges or cycles in the owner DAG;
- host implementations callable from an admitted device hot path;
- source-path/address/lane-derived semantic identities;
- compatibility schemas, defaulting decoders, fallback branches, or dual representations;
- file/module growth beyond the declared owner budget without a recorded decomposition decision;
- generated device binaries whose build manifest, architecture, or hashes are missing; and
- tests which grade only counts, hashes, timing, or topology when an actual deed is required.

The audit ratchets from zero allowances in new production code. Historical/reference directories
are outside the build and cannot satisfy or suppress an audit.
