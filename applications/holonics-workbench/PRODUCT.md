# Holonics command application: product context

## Register

[definition] Product context for the exterior `holonics` application. This file schedules no engine
or formal construction.

## Operator

[definition] The primary operator is Brandon, working locally on consumer hardware. The application
must expose the state and artifacts required to construct and examine morphology variants without
requiring hidden directories, process-memory continuity, copied addresses, or source inspection.

## Product purpose

[definition] The primary product is a persistent, explicit-root variant workspace. It makes the
actual lifecycle (admission, experiment definition, circulation, exterior return, cultivation,
evaluation, and export) observable and repeatable across separate commands. Low-level Eros,
Soulkiller, Athena, and engine mechanisms remain reachable under `diagnostic` when mechanism-level
inspection is the actual task.

## Interaction contract

[definition] The application should behave like a compact scientific instrument:

- creation names one explicit workspace root, then commands use that directory or `--root PATH`;
- `inspect` returns current generation, snapshot, experiments, active/completed runs, evaluations,
  exports, and named open capabilities;
- every successful mutation names the exact artifacts it wrote;
- active conduct and staged candidates survive process exit;
- committing, declining, withdrawing, replaying, and exporting are distinct visible deeds;
- human output gives the operational consequence first, while JSON/JSONL retain the complete wire;
  and
- refusals preserve the last admitted workspace state.

## Anti-references

[definition] The product is not:

- a CLI embedded inside terminal panes;
- a repository file explorer;
- a generic “discovery” browser;
- a raw JSON viewport presented as model understanding;
- a hidden user-local artifact store;
- a demo mistaken for model construction;
- a single prompt/output score mistaken for an inference evaluation; or
- a new semantic owner for mechanisms already present in the engine.

## Capability wording

[established-bounded; implemented-exact; source-inspected] The current application operates real
native morphology artifacts and actual returned excitation receipts. It persists structural
circulation/cultivation and exact export.

[open; source-inspected] It does not yet execute an arbitrary Hugging Face model directory, accept a
qualitative multimodal prompt, or emit a useful qualitative response. Those are explicit future
application/codec fibres, not features supplied by the bounded diagnostic demo.

## Presentation posture

[definition] No terminal UI is part of the current release. A future presentation is justified only
after the application lifecycle and the decisions it exposes are useful independently of that
presentation. Any later interface must render variant anatomy, current circulation, candidate
effects, evaluation comparisons, and artifact lineage from the standing application API rather
than inventing a second workflow.
